**explicit architectural responsibilities**, because they determine where the cryptographic logic belongs.

The clean model is:

| Question                                   | Responsibility                                                                                                                                                                    |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Who generates KEK?**                     | **Vault cryptographic authority** — generated when the Trust Group is created.                                                                                                    |
| **Who rotates KEK?**                       | **Vault / Trust Group authority**, through an authorized domain operation.                                                                                                        |
| **Who adds a member?**                     | **Trust Group authority** — an authorized existing member/admin, according to the Trust Group policy.                                                                             |
| **Who creates WrappedKEK?**                | **The member's/device's key-management context**, using the member's public encryption key.                                                                                       |
| **Who creates WrappedDEK?**                | **The sharing authority**, using the current KEK to wrap the DEK.                                                                                                                 |
| **Who can recover a key?**                 | **Only an authorized member/device that possesses the required private key/material and satisfies the recovery policy.**                                                          |
| **What happens when a member is removed?** | **Remove access and rotate the KEK.** Existing encrypted material should be re-associated with the new KEK through new wrapping; the removed member must not receive the new KEK. |
| **What happens when a device is lost?**    | **Revoke that device's key, prevent further access, and re-establish access from another authorized device.** Depending on the threat model, rotate affected keys.                |

But there is one important correction I would make to the terminology before you implement it.

### 1. KEK

The **KEK belongs to the Trust Group**, not to an individual user.

Conceptually:

```text
TrustGroup
   │
   └── KEK v1
         │
         ├── Member A → WrappedKEK(A)
         ├── Member B → WrappedKEK(B)
         └── Member C → WrappedKEK(C)
```

The KEK should therefore be generated by the **trusted vault cryptographic service**, not by the frontend and not by an arbitrary collaboration participant.

For example:

```text
CreateTrustGroup
    ↓
Generate KEK
    ↓
KEK v1
    ↓
Create member-specific WrappedKEK
```

The raw KEK should never be persisted as ordinary vault data.

---

### 2. WrappedKEK

This is where the member/device public key comes in.

For member `A`:

```text
KEK
  ↓ encrypt/wrap with A's public key
WrappedKEK(A)
```

Then:

```text
A's private key
      ↓
unwrap
      ↓
KEK
```

So the important distinction is:

> **The Trust Group owns the KEK; the member/device owns the ability to unwrap its WrappedKEK.**

This is particularly important for your federation model because the remote vault should never need to receive the plaintext KEK.

---

### 3. WrappedDEK

Your asset encryption should remain independent from the Trust Group key.

For example:

```text
Asset
  ↓
random DEK
  ↓
encrypt asset
  ↓
Encrypted Asset
```

Then:

```text
DEK
 ↓
wrap using current KEK
 ↓
WrappedDEK
```

So your existing:

```json
{
  "asset_cid": "bafy-asset-001",
  "trust_group_id": "tg-oem",
  "wrapped_dek": "..."
}
```

is conceptually correct.

The important property is that **the asset itself doesn't have to be re-encrypted when the KEK rotates**.

You can rotate the KEK and re-wrap the DEK:

```text
Old:

KEK v1
  ↓
WrappedDEK v1
  ↓
DEK
  ↓
Encrypted Asset


After rotation:

KEK v2
  ↓
WrappedDEK v2
  ↓
DEK
  ↓
same Encrypted Asset
```

That's a major architectural advantage.

---

## 4. KEK rotation

This is especially important for your C3 implementation.

When membership changes:

```text
KEK v1
   ↓
member removed
   ↓
generate KEK v2
   ↓
re-wrap required DEKs
   ↓
create WrappedKEK(v2) for remaining members
```

The removed member may still possess:

```text
KEK v1
```

Therefore **simply deleting their WrappedKEK is insufficient**.

They may already have decrypted the old KEK.

The new KEK is what provides cryptographic forward access isolation.

---

## 5. Member removal

I'd define the invariant as:

> **A removed member must never receive the current Trust Group KEK.**

Operationally:

```text
RemoveMember(A)
      │
      ├── revoke A's membership
      ├── revoke A's active devices
      ├── generate KEK v2
      ├── re-wrap DEKs with KEK v2
      └── distribute WrappedKEK(v2)
          ├── B
          └── C
```

You don't necessarily need to rewrite every encrypted asset.

That's why the DEK/KEK separation is valuable.

---

## 6. Lost device

A lost device is slightly different from a removed **member**.

You want:

```text
Member A
   ├── Device A1
   ├── Device A2
   └── Device A3
```

If A1 is lost:

```text
revoke Device A1
       ↓
A1 can no longer authenticate
       ↓
A2/A3 remain valid
```

You **do not necessarily remove Member A**.

This means your C3 model should probably distinguish:

```text
Member
   │
   └── Devices
          ├── DeviceKey A1
          ├── DeviceKey A2
          └── DeviceKey A3
```

That distinction will become very important when you implement recovery.

---

# The architecture I would lock in

For your C3 Vault, I'd establish these rules:

```text
                    TRUST GROUP
                         │
                    owns KEK vN
                         │
             ┌───────────┴───────────┐
             │                       │
          Member A                Member B
             │                       │
        Device A1                Device B1
             │                       │
       WrappedKEK(A)           WrappedKEK(B)
```

And separately:

```text
                    ASSET
                      │
                 random DEK
                      │
              encrypted content
                      │
                  WrappedDEK
                      │
                   KEK vN
```

This gives you a very clean separation:

**Identity / device layer**

```text
Who are you?
Can this device authenticate?
Is this device revoked?
```

**Trust Group layer**

```text
Are you a member?
What is the current KEK version?
Can you receive the KEK?
```

**Asset layer**

```text
What DEK protects this asset?
Which Trust Group controls access to that DEK?
```

**Federation layer**

```text
Can the remote vault participate?
Has the remote identity been trusted?
Which encrypted material may cross the federation boundary?
```

That fits extremely well with the C3 architecture you've already built.

### The eight answers I'd put into the architecture document

1. **KEK generation:** Trust Group cryptographic authority.
2. **KEK rotation:** Trust Group authority after membership/security events.
3. **Member addition:** Authorized Trust Group authority.
4. **WrappedKEK creation:** Vault cryptographic service for each authorized member/device public key.
5. **WrappedDEK creation:** Vault cryptographic service when an asset is shared, using the current Trust Group KEK.
6. **Key recovery:** Only authorized members/devices satisfying the Trust Group recovery policy.
7. **Member removal:** Revoke membership + rotate KEK + issue new WrappedKEKs + re-wrap DEKs as required.
8. **Lost device:** Revoke device key/session; preserve membership if the member remains authorized; recover through another trusted device/recovery mechanism.

**One thing I would *not* do:** let the frontend/client decide any of these cryptographic transitions. The client can request `AddMember`, `RotateKEK`, `RecoverKey`, `RevokeDevice`, etc., but the authoritative operation belongs in your backend/domain/crypto boundary.

That is consistent with the client/non-authoritative boundary you've been establishing.
